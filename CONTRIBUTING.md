# Contributing to Ramp Autonomy

Thanks for taking an interest. This project is a ROS 2 / Gazebo stack for ramp ascent and descent on a loaded wheeled AMR, and it cares a lot
about one thing in particular: **a claim is only as good as the evidence that separates it from the first plausible explanation.** That shapes
most of what follows.

## Ways to contribute

- **Report a bug.** Open an issue with the launch command, the world, the payload arguments, and what you expected versus what happened.
- **Reproduce a result.** The numbers in [`docs/results.md`](docs/results.md) come from a specific harness on a specific host. Independent
  reproduction - matching *or* contradicting - is genuinely useful, and a contradiction is more useful than a match.
- **Extend the simulation.** New ramp geometries, friction profiles, or payload configurations.
- **Work on an open limitation.** [`docs/known-limitations.md`](docs/known-limitations.md) lists what is actually still open and what is a
  standing scope boundary. The second category is deliberate - please read it before proposing work there.
- **Improve the docs.** Including this file.

## Getting set up

Build and run instructions, the full launch-argument table, and how to drive the validation suite are in
[`docs/getting-started.md`](docs/getting-started.md). The short version:

```bash
colcon build --symlink-install
source install/setup.bash
ros2 launch ramp_autonomy_bringup ramp_autonomy_bringup.launch.py world:=construction_site payload_mass:=100.0
```

Requirements: ROS 2 Jazzy, Gazebo `gz-sim` 8, Nav2, `robot_localization`, and `libxtensor-dev` for the MPPI critic plugins.

The validation scripts under `validation/phase8/` resolve the workspace root from `RAMP_WS`:

```bash
export RAMP_WS=/path/to/ramp_autonomy_ws
```

They exit with a message if it is unset rather than reading a wrong path.

## Opening a pull request

Fork the repo, push your branch to your fork, then open the PR with the base set to
`skunal3318/Ramp-Autonomy` and the `main` branch. GitHub sometimes pre-selects your own fork as the
base, which produces a PR that only you can see - if it does not appear in
[the pull request list here](https://github.com/skunal3318/Ramp-Autonomy/pulls), that is usually why.

## Before you open a pull request

1. **Build cleanly.** `colcon build --symlink-install` with no new warnings from the packages you touched.
2. **Say how you verified it.** This is the one thing that matters most here. "The FSM reaches EXIT" is not verification - the FSM reporting
   its own state is exactly the failure mode [`docs/retrospective.md`](docs/retrospective.md) documents twice. Verify against Gazebo ground
   truth, and say which run you looked at.
3. **Keep raw run data out of the commit.** The suite writes rosbags, per-topic traces and screen recordings; `.gitignore` already excludes
   them. Commit the analysis and the write-up, not the several GB that produced it. If a result needs a large artifact to be believable,
   mention it in the PR and it can go on a release instead.
4. **Match the surrounding style.** Python follows PEP 8 at the loose end; the existing code favours short modules with a docstring at the top
   stating what the file is for. C++ critic plugins follow the `nav2_mppi_controller` conventions they plug into.
5. **One concern per PR.** A geometry fix and a controller retune are two PRs.

## Changes that need discussion first

Open an issue before starting on:

- New dependencies, especially anything outside the ROS 2 / Gazebo ecosystem.
- Changes to the five-state ramp FSM contract (`APPROACH → ASCENT → TRANSITION → DESCENT → EXIT`, with `HALT` pre-emptable from any state).
- Changes to the construction-site world geometry. The site is a documented design with per-object real-world grounding and citations in
  [`docs/construction_site_design.md`](docs/construction_site_design.md); the layout is generated by
  `validation/phase8/floor2/generate_floor2.py` and checked by the clearance and seam tests beside it. Hand-editing the generated block in
  `construction_site.sdf` will be overwritten - change the generator.
- Anything that would change a published number in `docs/results.md`.

## Reporting a safety-relevant finding

If you find a case where the stack drives the robot into a state a real machine could not recover from - a tip-over, a ledge departure, a
runaway descent - please open an issue and label it clearly. The stability margin and descent braking exist precisely because those cases are
the point of the project, and a reproducible one is a valuable contribution.
